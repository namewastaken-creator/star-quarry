# Star Quarry

A 3D idle space-mining game (Three.js r128, plain HTML/JS, no framework). Players claim planets, run mining crews, smelt ore, research upgrades and warp to new galaxies. Published at https://namewastaken-creator.github.io/star-quarry/ (GitHub Pages from `main`) and as an Android app.

The whole game is one source file, `src/game.html`. See `BUILDING.md` for the layout, requirements and the full publish routine.

The game's rules, balance numbers and the history behind them are in `docs/design-notes.md`. Read the relevant section before changing gameplay, and add a short entry under "Later changes" at its end when a change alters rules, numbers or how a system works. Its sections on who changes the game and on publishing describe the old chat workflow; this file and `BUILDING.md` replace them.

## Golden rules

- **Never edit build outputs by hand.** `index.html`, `sw.js`, `version.json`, `manifest.webmanifest`, `three-r128.min.js` and `sky-*.jpg` at the repo root, and `android/app/src/main/assets/index.html`, are generated by the build. Edit `src/game.html` and rebuild.
- **Every publish bumps the version** with `src/bump.py`, then builds. Never change `APP_VER`, `CHANGES`, `src/changelog.json` or `version.json` by hand.
- **Work on `dev`**; merge to `main` only when a build is ready to publish. Pushing to `main` updates the live game for every player.
- **Never commit** the Android signing keystore, its passwords or `local.properties`.
- **Saves live in players' browsers.** Any change to the save format needs a migration and must never silently overwrite an existing save.
- **Publish only through the release routine** (`/release`, in `.claude/skills/release/SKILL.md`). Never merge into or push to `main` unless `tools/preflight.py` printed `READY TO PUBLISH` for that exact commit, and the user said yes in chat to publishing that version. Never force-push `main`.
- **On Windows, `python3` is the Microsoft Store shortcut:** use `python` for every command below.
- **Run multi-step commands so they stop at the first failure**, and check that a folder exists before running git in it, so a failed step can never carry on in the wrong repository.

## Versioning

Major.Minor.Patch.Build, shown as "Beta 0.x.y.n" while major is 0.

- **Minor:** a major new feature or block of content (patch resets to 0).
- **Patch:** fixes and small tweaks, including visual polish.
- **Build n:** +1 on every publish. Update checks compare only this, so it never goes backwards.
- `--important` asks players to update; use it only for fixes that matter.

Change-log entries are short, player-facing sentences: say what the player will notice, not how the code changed.

## Commands

Run from the repository root.

- **Bump:** `python3 -I src/bump.py "what changed"` (`--minor`, `--major`, `--important`; `--sync` rewrites `CHANGES` from `src/changelog.json` without a new version)
- **Build:** `python3 -I src/build.py` (runs `src/guidecheck.py`; if it warns that gameplay changed but the user guide didn't, update `GUIDE` in `src/game.html`, or rebuild with `--guide-ok` when the guide isn't affected)
- **Release gate:** `python3 -I tools/preflight.py` (run on `dev` after the release is committed and pushed; checks the branch, the version bump, a reproducible build and all the checks, and ends with `READY TO PUBLISH` or `NOT READY` plus a fix)
- **Check:** `python3 -I tools/check.py` (the headless browser tests in `tools/tests/`, including `pwsw`, which checks the offline copy can only ever be replaced by the real game, and `pwframe`, the late-game frame-time test that loads `tools/tests/lategame.json` (remake it with `tools/tests/mklategame.py`), plus the overlap check `tools/occcheck.py`; all must pass; needs `pip install playwright pillow` and `python3 -m playwright install chromium`)
- **Test locally:** serve the repo root (for example `python3 -m http.server 8000`) and open http://localhost:8000. Use the Preview pane to check changes visually; http://localhost:8000/src/artifact/preview.html?src=/index.html shows the built game in device-sized frames (Small, iPhone, Large Android, iPad mini, iPad Pro 13″, rotated).
- **Visual close-ups of the 3D scene:** `tools/featclose.py`, `tools/closeup.py`, `tools/eruptshots.py` and friends (usage at the top of each file; images go to `out/`).
- **Android:** build first, then open `android/` in Android Studio (see `BUILDING.md`).

## Testing changes

- Check visual changes in the Preview pane with screenshots before and after, including at phone width (about 390 px wide).
- Test with a late-game save (20+ planets, 3 crews, all research) as well as a new game; performance problems show up late.
- Watch the console for errors; the game swallows some of them (see `tabBadges`).

## Known issues to keep in mind

The 26 Oct 2026 code review is in `docs/code-review-2026-10-26.md`, with a status table at the top (checked 30 Oct 2026). Of its 18 items, 15 are fixed; the high-priority four are guarded by tests (`pwframe`, `pwsw`, `pwbadsave`). Still open from it:

- **Readability (17):** very long source lines, a 40-branch `if/else` click handler (an `ACTIONS` table would be clearer), and migrations that all run on every load (an `S.mig` version and an ordered list).
- **File size (16, partly):** Three.js and the sky are separate cached files, but `index.html` is still about 750 KB per release.
- **Getters (14, partly):** `econG`, `galNow` and `fmt` still guard with `typeof S` because of load order.

Also open:

- Backups of unreadable saves (`starquarry_save_v1_bak`, `starquarry_save_v1_bak_<time>`) are kept, but players have no in-game way to export or restore them.
- `.claude/launch.json` hard-codes port 8000, so the Preview pane's server can't start while another server holds that port.
- The Preview pane's browser currently refuses to register any service worker; test offline behaviour with `pwsw` or headless Chromium instead.
